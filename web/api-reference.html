API Reference

API Reference

Two authentication schemes cover the whole API: an API key for the event chain and MCP gateway, and a JWT session for the dashboard. Every endpoint below notes which one it expects.

Authentication

SchemeHeaderUsed by
API key Authorization: Bearer tsk_... Events API (/v1/events*) and the native MCP gateway (/mcp/v1/rpc). Tenant and project are resolved from the key itself.
JWT session Authorization: Bearer <access token> Everything under /api/tenants/:id/* and /api/admin/* — the dashboard.

API keys carry a scope that limits what they can do — ingest (write-only), read (read-only), or admin (both). Keys are generated with prefix tsk_, shown in full exactly once at creation time, and stored server-side only as a SHA-256 hash — losing it means revoking and issuing a new one.

Events API — the hash-chained event log

Scoped to one project at a time (resolved from the API key). This is the core, verifiable chain — see the Introduction for how hashing works.

POST/v1/eventsAPI key · ingest/admin
// request
{
  "event_type": "tools/call",
  "actor_id": "agent-a1b2c3",
  "payload": { /* any JSON */ },
  "occurred_at": "2026-09-20T10:00:00Z"  // optional
}
// 201 response
{ "event": { "id", "sequence", "hash", "prev_hash", ... } }

Optional Idempotency-Key header prevents duplicate ingestion on retry. occurred_at is accepted but the server-assigned sequence is what orders the chain — a client's clock can never reorder it.

All /v1/events* endpoints are rate-limited. A rejected request returns 429 with a Retry-After header — see Rate limits & quotas, and note that 429 has two distinct causes.

POST/v1/events/batchAPI key · ingest/admin

Body: {"events": [IngestRequest, ...]}, max 500 per batch. Each event is appended individually — a failure partway through does not roll back the ones that already succeeded.

{
  "results": [ { "index": 0, "event": {...} }, { "index": 1, "error": "quota_exceeded" } ],
  "success_count": 1,
  "total_count": 2
}

Status is 201 if every event succeeded, 207 (Multi-Status) if some failed, 400 if none did.

GET/v1/eventsAPI key · read/admin

Cursor-paginated query. Params: event_type, actor_id, since/until (RFC3339), cursor, limit (default 100). Response: {"events": [...], "next_cursor": "..."}.

POST/v1/events/verifyAPI key · read/admin

Body optional: {"from_sequence": 1} — omit to verify the whole chain from the start.

// valid
{ "valid": true, "checked_count": 4821, "from_sequence": 1 }

// broken
{ "valid": false, "checked_count": 4821, "from_sequence": 1, "broken_at_event_id": "evt_..." }

A broken chain triggers an internal alert every time — it's treated as a possible tampering incident, not a routine warning.

GET/v1/events/exportAPI key · read/admin

Params: format (json default or csv), same filters as the query endpoint, plus max (default 10,000, hard cap 100,000 per request). Returns a file download (Content-Disposition: attachment).

Two different limits apply, and they are not the same thing. The max ceiling of 100,000 is per request and applies on every plan — to export a larger range, repeat the request with narrower since/until windows. Separately, the Free plan is capped at the newest 100 events per export, which is a plan limit rather than a page size: a Free tenant that has stored 5,000 events will receive 100 of them in a file export. Pro and Business carry no plan cap.

Any response shortened by either limit carries X-Export-Capped: true, and plan-capped responses also carry X-Export-Plan-Cap. If you need every event on the Free plan, use the cursor-paginated GET /v1/events endpoint instead — it is not plan-capped on any tier, so your data is always fully retrievable.

Rate limits & quotas

Two independent mechanisms protect the API, and they fail in different ways for different reasons. Confusing them is the most common integration mistake, because both return HTTP 429.

Rate limitMonthly quota
Measured overA fixed one-minute windowYour billing month
Error body{"error": "rate_limit_exceeded", "limit": 1000, "priority": "normal"}{"error": "quota_exceeded"}
Retry-AfterSent — seconds until the window resetsNot sent
How to recoverBack off and retry; it clears on its own within the minuteUpgrade your plan, or wait for the next billing month
Scales with planMCP gateway: yes. Events API: no — it is a flat safety ceiling.Yes
Always branch on the error field, not on the status code. Retrying a quota_exceeded response will never succeed, and treating a rate_limit_exceeded response as a hard failure will drop events you were entitled to send. Honour Retry-After when it is present. 
// 429 — rate limit
// Retry-After: 23
{ "error": "rate_limit_exceeded",
  "limit": 1000,
  "priority": "normal" }

// 429 — monthly quota (no Retry-After)
{ "error": "quota_exceeded" }

priority tells you which limiter rejected the call: mcp for gateway traffic, normal for everything else. limit is the ceiling that was applied, so a Business tenant seeing "limit": 60 on MCP traffic is a bug worth reporting.

MCP gateway — per minute, by plan

Applies to /mcp/v1/rpc and /api/tenants/:id/mcp/*. The window is fixed, not sliding: it is aligned to the clock minute, so the counter resets on the minute rather than exactly 60 seconds after your first call.

PlanRequests / minute
Free60
Pro300
Business1,000

Events API — per minute, flat

/v1/events, /v1/events/batch, /v1/events/verify and /v1/events/export share one limit of 1,000 requests per minute per API key on every plan. This is an abuse and runaway-loop ceiling, not a billing lever — your paid volume is governed by the monthly quota below, not by this number. Use /v1/events/batch (up to 500 events per call) to stay well under it: 1,000 batched calls per minute carries up to 500,000 events.

Events already written stay intact and verifiable when you hit the quota — ingestion stops, the chain is never truncated. Upgrades apply immediately rather than at the next billing cycle. See Plans & quotas for the full comparison.

Authentication limits

Login has its own limiter, separate from everything above: 12 failures per minute per IP + email, and 30 attempts per minute per IP. An account locks for 15 minutes after 10 failures within 10 minutes.

Built-in tool types: health_check, metadata_lookup, echo, audit_lookup (queries the audit trail directly as a tool call, same data as the resources/read audit-log resource). Built-in prompts: audit-investigate, agent-health-report, tool-failure-triage.

Custom prompts are Business-only, Owner-only, and dashboard-only in practice. prompts/create/update/delete check the caller's role and plan tier via internal headers set by the dashboard session — an API key has no concept of "role," so those three methods always reject calls made through /mcp/v1/rpc, regardless of the key's scope or the tenant's plan.

Upgrading to Pro or Business auto-provisions two extra roles for the tenant — admin (full operational access, excluding billing and compliance/delete actions) and member (read-only, plus tool.execute and mcp.query so day-to-day use still works). Free-tier tenants only have the owner role.

A failed payment gives roughly a 4-day grace period before the tenant is auto-downgraded to Free (status becomes canceled_nonpayment, distinct from a voluntary canceled).

Health & operations

Two separate probes, deliberately. Mixing them up is how a healthy process gets killed in a restart loop.

GET/healthzpublic

Liveness. Answers 200 as long as the process is running and able to serve HTTP. It touches no database, so a database outage will never make it fail. This is the endpoint an orchestrator should use to decide whether to restart the container — if it used a database-backed check instead, a brief database blip would restart a process that was working fine, and the restart would not fix anything.

GET/readyzpublic

Readiness. Checks each dependency and returns 200 when the instance can serve real traffic, 503 when it cannot. Use this one as the load-balancer and deploy health check.

// 200
{ "status": "ready",
  "checks": { "bolt": "ok", "postgres": "ok" } }

// 503
{ "status": "not_ready",
  "checks": { "bolt": "error: timeout", "postgres": "ok" } }

Each check has a 2-second timeout, so /readyz cannot hang behind a stuck dependency. A component reported as not_configured is optional and does not make the instance unready.

GET/api/admin/backup/boltroot API key

Returns a consistent snapshot of the embedded key-value store as a file download, taken inside a read transaction so it is safe to call while the service is handling writes. Requires the X-Root-API-Key header; it is an operator endpoint, not a tenant one.

The response carries X-TrailSeal-Bolt-Size, the exact byte count of the snapshot. Compare it against the file you received — that header is how you tell a complete backup from a truncated one. The snapshot is assembled in full before the first byte is sent, so a failure mid-snapshot surfaces as a 500 rather than as a 200 carrying a half-written file.

Error reference

REST endpoints return {"error": "code"} (sometimes with extra fields, e.g. valid_scopes). MCP errors use a separate taxonomy, mapped to JSON-RPC error codes:

MCP error codeJSON-RPC codeMeaning
invalid_request-32602Malformed or missing required params.
tool_not_found-32602No tool matches the given name/ID for this tenant.
resource_not_found-32602Unknown resource URI.
prompt_not_found-32602Unknown prompt name.
quota_exceeded-32600Monthly event quota hit. Over MCP this arrives as JSON-RPC -32600 (not -32603): the request was understood and refused, so it is not a server fault and retrying will not help until the quota period rolls over. Over REST the same condition is a 429 with no Retry-After. Billable MCP methods are tools/call, resources/read and prompts/get; each successful call consumes one event. Calls that fail validation — an unknown prompt name, a missing argument — consume nothing.
rate_limit_exceeded—Too many requests this minute. REST 429 with a Retry-After header; clears on its own. The body also carries limit and priority. See Rate limits & quotas.
forbidden-32600Caller isn't allowed to do this (e.g. non-Owner calling prompts/create).
internal_error-32603Unhandled server error — details are never leaked to the response.
