Introduction

TrailSeal is an append-only, hash-chained audit log and MCP gateway built for systems where LLM agents call tools on your behalf. It sits in front of your agents, captures every call as a verifiable event, and gives you a tamper-evident record you can prove, not just store.

How it fits into your stack

Your agents talk to TrailSeal's MCP gateway instead of calling tools directly. Every tool call, prompt invocation, and resource read that passes through the gateway is written once to the immutable event chain and hash-linked to the event before it. Nothing is edited or deleted after the fact — if someone tampers with a past event, every event after it fails verification.

This event chain is separate from the audit trail shown on the dashboard's Audit page, which logs account-level activity (logins, user changes, API requests) rather than agent tool calls, and isn't hash-chained — it's the more familiar kind of audit log, aimed at compliance and forensics rather than cryptographic proof.

Everything in TrailSeal is scoped to a tenant at the database layer, so multiple teams or customers can run on the same deployment without their data or API keys ever crossing over.

Core concepts

Tenant

The top-level account boundary. Projects, API keys, agents, and audit events all belong to exactly one tenant.

Project

A workspace inside a tenant that groups related API keys, agents, and events — typically one per application or environment.

API key

Authenticates requests to TrailSeal. Every key is issued with a scope — ingest, read, or admin — that limits what it can do.

Agent

A registered LLM agent that calls through the gateway. Agents carry a status — active, inactive, or error — that you can monitor and update.

Role

Every tenant starts with a full-access owner. Upgrading to Pro or Business auto-provisions admin (full operational access, no billing/compliance) and member (read-only plus tool execution).

Event (chain)

An immutable, hash-chained record of one gateway call. Verifiable at any time via /v1/events/verify. Not the same as an audit log entry — see below.

Audit trail entry

A record of account-level activity — logins, user changes, API requests — with an outcome of success, failure, or denied. Not hash-chained.

Retention & anonymization

Audit trail entries are kept up to your plan's retention ceiling — 14 days (Free), 180 days (Pro), 365 days (Business) — and their PII is scrubbed after a separate, tenant-configurable anonymization window. You can shorten retention below the ceiling, never extend past it.

Tools, prompts & resources

TrailSeal speaks the Model Context Protocol (MCP), so the gateway exposes three kinds of primitives to your agents:

Only successful calls to these three MCP methods — tools/call, resources/read, and prompts/get — count toward your plan's billed events. Your monthly quota, on the other hand, counts every attempt, including failed ones — so the two numbers on your dashboard won't always match, by design.

There are two ways to reach the gateway, depending on who's calling: /mcp/v1/rpc authenticates purely off the API key (the tenant is resolved from the key itself) — this is what external clients like Claude Desktop or Claude Code connect to. /api/tenants/:id/mcp/rpc instead requires the dashboard's JWT session, for calls made from your own logged-in session rather than an API key.

Tools

Actions an agent can invoke through the gateway. Every call is written to the event chain before the result is returned.

Prompts

Reusable, parameterized prompt templates agents can request by name, with typed arguments.

Resources

Readable data exposed to agents by URI — for example trailseal://audit-log — each with its own content shape.

Events, verification & retention

Every event ingested by TrailSeal is chained by hash to the one before it. The public, API-key-authenticated way to check this is POST /v1/events/verify, alongside the same family as POST /v1/events (ingest), /v1/events/batch, and GET /v1/events/export:

bash
curl -X POST https://api.trailseal.dev/v1/events/verify \
  -H "Authorization: Bearer YOUR_API_KEY"

The dashboard's Chain integrity card is a separate, one-click version of this aimed at logged-in users — Valid, Broken (with the first event where the chain breaks), or "no events yet." It's backed by an incremental verification pass on refresh, so it stays fast even at large event volumes, with a full recheck run automatically on every manual "Verify now."

Retention days are always capped by your plan tier — you can set a shorter window, never a longer one, and downgrading a plan clamps any existing override down to the new ceiling. Monthly event quotas follow the same plan-scaling rule; upgrading applies a new limit immediately rather than waiting for the next billing cycle. Only a tenant Owner can change the retention window.

Quickstart

This mirrors the "Get started" checklist on your dashboard's Overview page — three steps from an empty tenant to your first recorded, verifiable event:

1. Create a tool

From the Tools page, add your first tool. Pick a preset like health_check to try it fast.

2. Generate an API key

From the API Keys page, create a key for a project, scoped to what it actually needs (ingest, read, or admin).

3. Connect a client

Use the MCP Test Console at the bottom of the Tools page, or connect a real client like Claude Code — see the command below.

From the API Keys page, revealing a new key also gives you a ready-to-run command to register TrailSeal as an MCP server:

bash
claude mcp add trailseal --transport http \
  https://api.trailseal.dev/mcp/v1/rpc \
  --header "Authorization: Bearer YOUR_API_KEY"

/mcp/v1/rpc authenticates purely off the API key — no separate tenant ID needed, it's resolved from the key itself. Swap the URL for your own NEXT_PUBLIC_API_BASE_URL if you're self-hosting.

The "Get started" card on your Overview page disappears automatically once that first successful call is recorded as a billed event.
